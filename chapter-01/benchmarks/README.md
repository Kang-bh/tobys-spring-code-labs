# 1.6 객체 생성과 싱글톤 재사용 성능 실험

“요청당 객체 5개 × 초당 요청 500개 = 초당 객체 2,500개”는 객체 **개수**의 계산이다. 개수만으로 서버가 부하를 감당할 수 없는지는 알 수 없다. 이 실험은 요청 하나에 해당하는 작업에서 객체 다섯 개를 새로 만드는 경우와, 스프링 컨테이너가 만든 불변 싱글톤 빈 다섯 개를 재사용하는 경우를 비교한다.

## 실행

저장소 루트에서 Java 17 이상과 Maven으로 실행한다. `mvn test`에서는 벤치마크를 실행하지 않는다.

```bash
mvn -pl chapter-01/benchmarks -am -DskipTests package
java -jar chapter-01/benchmarks/target/benchmarks.jar ObjectCreationBenchmark -f 2 -wi 5 -i 5 -w 2s -r 2s -t 1 -prof gc
```

짧게 동작을 확인할 때는 `-f 1 -wi 2 -i 3 -w 1s -r 1s`로 줄일 수 있다. 공유 싱글톤을 여러 스레드에서 실행해 보려면 `-t 4`처럼 스레드 수를 바꾼다. 결과는 장비, JDK, GC, 워밍업 조건에 따라 달라진다.

## 읽을 지표

| JMH 출력 | 의미 | 500 요청/초에 적용 |
| --- | --- | --- |
| `gc.alloc.rate.norm` (B/op) | 요청 하나에 해당하는 작업의 평균 할당 바이트 | B/op × 500 = 예상 할당 B/s |
| `avgt` (µs/op) | 작은 작업 하나의 평균 실행 시간 | 두 구현의 미시적 비용 비교에만 사용 |
| `gc.count`, `gc.time` | 벤치마크 실행 중의 GC 횟수와 시간 | JMH가 최대 속도로 실행한 결과이므로 500 요청/초의 GC 횟수로 해석하지 않음 |

`ObjectCreationBenchmark`의 한 작업은 실제 HTTP 요청이나 DB 접근을 포함하지 않는다. `Blackhole`에 객체 참조를 전달해 JIT가 새 객체 생성을 제거하지 못하게 하고, 두 경로는 같은 계산을 한다. 컨테이너 초기화는 측정 구간 밖에서 한 번만 한다. 실제 서비스의 처리량, p95/p99 응답 시간, GC 지연은 HTTP 서버를 두고 목표 부하(예: 500 요청/초)에서 별도로 측정해야 한다.

## 실행 예시

로컬 JDK 21.0.10에서 1스레드, 1포크, 워밍업 2회와 측정 3회(각 1초)로 실행한 예시다. 수치는 환경에 따라 달라진다.

| 경로 | 할당량 (`gc.alloc.rate.norm`) | 평균 작업 시간 (`avgt`) | 500 작업/초로 환산한 할당량 |
| --- | ---: | ---: | ---: |
| 매번 5개 생성 | 80 B/op | 약 0.006 µs/op | 약 40,000 B/s (39 KiB/s) |
| 싱글톤 5개 재사용 | 거의 0 B/op | 약 0.002 µs/op | 거의 0 B/s |

이 실험에서는 새 객체 할당량 차이를 확인할 수 있지만, 39 KiB/s만으로 서비스에 GC 병목이 생긴다고 결론 내릴 수는 없다. 작업 시간은 극히 작은 계산의 결과이며, 스프링 컨테이너 조회·HTTP 요청·DB 작업의 시간을 나타내지 않는다. 위 환산값은 실제로 초당 500요청을 가한 측정값이 아니다.

싱글톤으로 재사용하는 객체는 요청별 변경 상태를 공유하지 않아야 한다. 이 실험의 다섯 객체는 불변 값만 가진다.
